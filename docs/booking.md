# Calendar booking

The existing morisoba Cloudflare Worker serves the calendar frontend and API on calendar.morisoba.moe. See [deployment and custom domain](calendar-domain.md). The website’s GitHub Pages deployment is independent and remains unchanged.

Native HTML/JS using shared chrome and typography. Worker APIs check Google Calendar free/busy and create invitations. Visitors need no Google login.

## Enable

1. Apply migration to the existing database:
   npx wrangler d1 migrations apply morisoba-mimorigasaka --remote
2. Create a Google OAuth web application with Calendar API enabled. Authorize the host account for offline access with scopes https://www.googleapis.com/auth/calendar.events and https://www.googleapis.com/auth/calendar.freebusy. Store these Worker secrets:
   - BOOKING_GOOGLE_CLIENT_ID
   - BOOKING_GOOGLE_CLIENT_SECRET
   - BOOKING_GOOGLE_REFRESH_TOKEN
   - BOOKING_CALENDAR_ID (usually primary)
3. Optionally set BOOKING_TIMEZONE (defaults to America/New_York). Defaults: weekdays 13:00–17:00 host time, 30-minute slots, 24-hour notice, 30-day horizon. Adjust validSlot in middleware/booking.mjs.
4. Deploy with the existing Cloudflare integration. Verify slots, a real invitation, and cancellation against the host calendar.

Without configuration the UI explicitly says booking is not open. GitHub Pages alone cannot run the API. Secrets stay server-side. No homepage navigation is changed until booking is ready.

## Persistence and conflicts

booking_reservations stores event ID, start, status, random cancellation token and creation time. Guest name/email/notes live in Google Calendar. A partial unique index atomically prevents two app requests claiming the same half-hour. Calendar is checked immediately before reservation. External calendar edits can still race this check: Google offers no atomic free/busy plus insertion.

An ambiguous Calendar or confirmation failure keeps the slot pending to prevent duplicate invitations. Reconcile pending rows manually using the row's event ID: mark confirmed if the event exists; otherwise mark cancelled to release. Never release solely by age.

Cancellation uses a long bearer token in the URL fragment; treat the saved link as private. Google sends invitations/cancellations through sendUpdates=all. Confirmation offers an ICS download and cancellation link. Rescheduling updates the same Google event and emails its attendees. Invitations include a private /manage link. Booking pages can enable automatic Google Meet links and email reminders.

Before public launch, configure Cloudflare rate limiting/Turnstile on the reservation API to control invitation spam. The honeypot only filters basic bots.

# Calendar portal

## URLs

- calendar.morisoba.moe/admin/ — password-protected management
- calendar.morisoba.moe/<booking_name> — guest booking page
- morisoba.moe/book/admin/ — fallback portal on the main Worker

Create and edit booking pages, set duration, weekday hours, timezone, notice and booking horizon, and pause bookings. Booking names are immutable after creation. All pages share the configured Google Calendar. A quarter-hour lock table prevents overlapping bookings across page types and durations. The /default page preserves the initial configuration.

## Password

Set BOOKING_ADMIN_PASSWORD_HASH to a scrypt record generated by scripts/booking-password.mjs. Generate a password of at least 16 characters. Supply it through stdin; never pass it as a command-line argument or commit it. Pipe the script's stdout directly into the secret store:

    node scripts/booking-password.mjs | npx wrangler secret put BOOKING_ADMIN_PASSWORD_HASH

The pipeline reads the password from stdin. The secret sets the initial password. After the first change in the portal, the current scrypt hash is stored in booking_admin_credentials in D1 and takes precedence over the bootstrap secret. Use Password → Change password to choose a new password. It requires the current password, checks confirmation and revokes every session. If you forget it, recovery requires an operator with database/secret access; there is no public reset link. Sessions use opaque tokens in HttpOnly, Secure, SameSite=Strict cookies, expire after 24 hours and are revoked by sign-out. Mutations require the same origin and a CSRF token. Login attempts are limited to eight per IP per 15 minutes; guest reservations to five per IP per window.

Apply migrations 0003, 0004 and 0005 before deploying. Keep existing bindings and tables. Portal records persist in D1.

## Subdomain

Attach calendar.morisoba.moe as an additional Custom Domain to the existing morisoba Worker in Cloudflare, preserving existing domains and routes. All requests run through the Worker so protected HTML and named booking paths cannot bypass routing via static assets. BOOKING_HOST can override the expected hostname.

The separately hosted private preview uses the same booking modules with its own database. Its records and password do not configure the original Worker automatically. Do not point the subdomain at both deployments.

## Guest access

Only administration requires the password. Guest booking pages are available with a page link once the host is public. Paused and unknown pages return 404. The private preview also requires its hosting account's sign-in. Calendar credentials remain server-side; availability stays closed until configured.


## Guest booking management

Migration 0006 adds operation tracking for reschedules and cancellations. Apply it before deploying this version. Guests open `/manage#token=...` from their invitation or confirmation. Tokens are sent only in same-origin POST bodies; the page uses no-referrer and no-store responses. Pausing a page disables new bookings and rescheduling but leaves cancellation available.

Rescheduling locks the replacement interval while keeping the original interval reserved, then patches the existing Google event with its ETag and `sendUpdates=all`. A successful update releases the original locks. An uncertain response retains both intervals; the next management read reconciles only a matching Google event. Unresolved operations require operator review, never automatic time-based lock release. Cancellation uses the same operation tracking and requests notification delivery to all attendees.

Google Calendar sends invitation, change, and cancellation emails. Delivery timing and spam filtering are controlled by Google and recipient providers; this is not a separate branded email service. The app sends separate Gmail reminders when enabled; attendees can also use their own calendar reminders. The downloadable ICS uses the Google event's UID to avoid a separate event identity.

The admin portal lists upcoming bookings and verifies calendar access using the free/busy API. The OAuth app must be in production for an enduring connection; Google's testing-mode refresh tokens for Calendar scopes expire after seven days. The initial connection uses an operator-only loopback OAuth callback, and all credentials are installed as Worker secrets, outside this repository. Reauthorization currently requires the operator flow.

## Personal scheduling options

Apply migration 0007 before deployment. Each page supports optional Google Meet links, buffers before/after meetings (0–120 minutes in 15-minute steps), and a per-page daily booking limit (0 is unlimited). Limits use the host timezone and include pending reschedules. Existing bookings retain their buffer and reminder settings.

The Worker checks reminders every five minutes, sending at approximately 24 hours and 1 hour before the booking. Bookings made after a reminder threshold do not receive that reminder. Google OAuth requires gmail.send, calendar.events, and calendar.freebusy. Gmail access is send-only. Each recipient/reminder/time is durably claimed before sending to avoid duplicates; uncertain or failed sends are not automatically retried and appear in the admin booking list for attention. Cancellation and in-progress updates suppress reminders.

New bookings also send a separate Gmail receipt to the event organizer, with guest details, time, meeting link, notes, and the private management link. This is independent of Google Calendar's attendee invitations. Host receipts are recorded in the delivery ledger as `host-booked`; email failure preserves the confirmed booking and shows an email-delivery warning in admin.

## Booking abuse protection

Migration 0008 adds hashed email identifiers and persistent rate-limit counters. Direct booking is enabled; email verification codes are not required and the former verification endpoint is disabled. The unused verification table is retained for migration compatibility.

Across all booking pages, an address may have three upcoming pending/confirmed bookings and create five bookings per rolling 24 hours (including cancelled bookings). Gmail dot/plus aliases share limits. The overall creation cap is twenty bookings per rolling 24 hours. Legacy reservations without email hashes do not count toward address caps. Reservation insertion and cap enforcement are atomic.

Reservation attempts retain the five-per-IP-per-fifteen-minute limit. Availability is limited to sixty requests per IP per five minutes. IPs come from Cloudflare's connecting-IP header, not client JSON or X-Forwarded-For. The honeypot, same-origin checks, input validation, and slot locks remain in place. Without email verification, address caps are abuse controls, not proof of mailbox ownership; multiple addresses/IPs remain a limitation.
